# Validation run: depexit on a second project (understatAPI)

**Result: depexit ran end to end on a project it was not built around, and every migration it tested passed.**
3 at-risk dependencies were found, Gemma 4 proposed a change for each, and each change was applied to a copy of the
project and checked against the project's own test suite (**31 tests plus 2,011 subtests, all passing before and
after every change**). Gemma's three predictions were all correct.

> Read [Section 6](#6-what-this-does-and-does-not-show) before quoting these numbers. The migrations here are easy
> ones (removing old pins of transitive dependencies), so this shows that the pipeline works on a second real project,
> not that Gemma is reliable on hard migrations.

---

## 1. Why we ran this

Our main run is on LinkWatch, the organisers' repository, which was chosen because it is full of planted
dependency problems. A tool that only works on the one repository it was built against proves little, so we
re-ran the whole pipeline on an unrelated project to check that nothing in depexit is specific to LinkWatch.

## 2. The target and how we chose it

| | |
|---|---|
| Project | [`collinb9/understatAPI`](https://github.com/collinb9/understatAPI), a small Python API for scraping football data from understat.com (MIT licence) |
| Commit tested | `d1252d9734e94ba98c681d2e41d467f1edb7aaf5` |
| Dependencies | 5 in `requirements.txt` (`requests`, `certifi`, `charset-normalizer`, `idna`, `urllib3`). Only `requests` is a real direct dependency: the project's `requirements.in` says `requests>=2.31.0`, and the other four are transitive pins generated by `pip-compile` |
| Test suite | pytest, `test/test_api.py` (31 test functions, 8 of them with subtests). The HTTP layer is mocked (`test/mock_requests.py`), so it runs offline; no extra plugins or services needed |

We looked for a project where the baseline tests actually run. About 160 candidate repositories were screened
from GitHub code search (old pinned versions in `requirements.txt`), reduced by size, number of pins, presence of tests
and pytest configuration, and then the **baseline run was tried** on the survivors. Most failed for reasons outside
depexit's control, which is a finding in itself:

| Candidate | What happened on the baseline run (Python 3.12, Windows) |
|---|---|
| **understatAPI** | **Tests ran: 31 tests + 2,011 subtests, all pass. Used for this validation.** |
| udemy-bot | Old `boto3` breaks test collection (`No module named 'botocore.vendored.six.moves'`): 0 tests ran |
| scrapydweb | Collection error: `pkg_resources` missing (APScheduler 3.6.0 needs it; newest setuptools no longer ships it) |
| Topaz | Collection error inside an old vendored `py`/`apipkg` |
| fastapi-redis-cache | `uvicorn==0.14.0` would not install |
| diffy | `python-levenshtein==0.12.0` needs a C++ compiler to build |
| http-prompt | Its pytest configuration requires the `pytest-cov` plugin, which depexit does not install: 0 tests ran |

## 3. How the run was done

```powershell
python -m depexit analyze https://github.com/collinb9/understatAPI --review --out validation_run
```

| | |
|---|---|
| Date | 15 October 2026, started 11:05 UTC, finished 11:12 UTC (433 s) |
| Test environment | Python **3.12.5**, a fresh virtual environment per run (depexit itself ran on Python 3.14.7) |
| Install | `pip install -r requirements.txt pytest` |
| Test command | `python -m pytest -q -W default -p no:cacheprovider --junitxml=junit.xml` (identical for the baseline and every candidate) |
| AI | Gemma 4 through the Gemini API: `gemma-4-31b-it` answered idna and certifi, `gemma-4-26b-a4b-it` (the automatic fallback) answered urllib3 |
| Options | `--review` (the optional second-opinion step, see Section 5) |

The Gemma API returned HTTP 500 errors for some calls during this session. The first attempt at this run recorded
those as handled AI failures (no crash); this documented run is the re-run in which they succeeded, with answers
for `idna` and `certifi` reused from the first attempt's cache.

## 4. Results

### Summary

| Dependency | Health | Gemma's change | Model | Tests after the change | Verdict | Prediction |
|---|---|---|---|---|---|---|
| idna | 45 | remove the `idna==2.10` pin | 31B | 31 passed + 2,011 subtests passed | same (nothing broke) | pass, **correct** |
| urllib3 | 45 | remove the `urllib3==1.26.5` pin | 26B | 31 passed + 2,011 subtests passed | same | pass, **correct** |
| certifi | 65 | remove the `certifi==2025.11.12` pin | 31B | 31 passed + 2,011 subtests passed | same | pass, **correct** |

**Baseline** (original dependencies): 31 tests and 2,011 subtests passed, 0 failed, 0 errors, no warnings.
**Scorecard: 3 graded, 3 correct (accuracy 1.0).**

depexit's report counts each subtest as a test, so it prints `2042/2042`. That is the junit total
(31 + 2,011 = 2,042); the pytest summary line in the logs shows the breakdown.

"Same" is depexit's verdict for a migration that installs and breaks no test that passed before. Nothing in the
suite was failing beforehand, so there was nothing for the migrations to fix.

| Run | idna | urllib3 | certifi |
|---|---|---|---|
| Baseline (original pins) | 2.10 | 1.26.5 | 2025.11.12 |
| After removing idna's pin | **3.20** | 1.26.5 | 2025.11.12 |

`requests==2.32.5` and `charset-normalizer==3.4.4` were unchanged in every run. In each case pip resolved the

## 5. The optional second opinion (`--review`)

After a migration has been tested, `--review` asks Gemma what the passing tests may **not** have covered, giving it
the measured results as facts. Its output is AI-suggested, and the capsule labels it that way.

| Dependency | Residual risk | Agrees with the verdict? | What it said the tests may have missed |
|---|---|---|---|
| idna | medium | yes | URLs with non-ASCII (internationalized) domain names; punycode edge cases; API changes between idna 2.x and 3.x |
| urllib3 | medium | **no** | whether `requests` is mocked in the tests, so real TLS/SSL handshakes may be untested; urllib3 2.x connection pooling and retry changes; OpenSSL version requirements |
| certifi | not available | not available | the review call hit a Gemma API 500 error and was recorded as a failure |

The `urllib3` disagreement is the most interesting output: the tests passed, but Gemma pointed out that a mocked test
suite would not notice changes in urllib3 2.x's TLS behaviour. We checked the first half: the project's tests do mock
the HTTP layer (`test/mock_requests.py`), so no real TLS handshake is exercised. The claims about urllib3 2.x
itself are AI-suggested and were not verified; they are for a maintainer to follow up.

## 6. What this does and does not show

**It shows**
- The pipeline works end to end on a second, unrelated project: it read the dependencies, scanned the code, scored
  risk from PyPI, asked Gemma 4, applied each plan to an isolated copy, ran the project's real tests against each
  change, compared them with the baseline, and wrote the capsule.
- The "tests decide, not the AI" idea held up: each prediction was checked against a real test run with a
  genuinely different dependency version installed (Section 4).
- Errors were handled without crashing: when Gemma's API failed, depexit recorded it and carried on.

**It does not show**
- **That Gemma handles hard migrations.** Removing a pin of a transitive dependency is the easiest kind of change.
  A harder test is the main run on LinkWatch, where Gemma rewrote source files.
- **That the project is safe on the newer versions.** The suite passes with idna 3.20, urllib3 2.8.0 and
  certifi 2026.7.22, but the suite is small (31 test functions) and, as Gemma's review notes, it may mock the
  network. "No test broke" is not a guarantee.
- **A real fix to the project.** understatAPI's `requirements.txt` is generated by `pip-compile` from a
  `requirements.in` (the file says so, and every line has a `# via` comment). Removing lines from the generated file
  would be undone the next time it is regenerated. The correct place for such a change is `requirements.in`
  (`requests>=2.31.0`), which depexit does not read. The finding is still useful: the project passes its tests with newer transitive versions.
- **Anything about the transitive pins being "unused".** depexit marks them unused because nothing imports them
  directly. They are in fact required by `requests`.
- **Run-to-run stability.** Gemma's answers are not deterministic and the hosted API was intermittently failing.
  Re-running may give different plans, so the capsule stores the exact answers and prompts used (`ai/`).

## 7. Evidence and how to check it

Everything in this folder was produced by the run above (22 files, about 130 KB, no secrets):

```text
validation/understatAPI/
  VALIDATION.md        this document
  report.html          the interactive report (open in a browser, works offline)
  summary.json         all data, plus a SHA-256 fingerprint of each evidence file
  replay.ps1           re-runs every command so the results can be re-checked
  idna/ urllib3/ certifi/
      capsule.md       verified facts, then Gemma's suggestion, then open concerns
      capsule.json     the same, machine-readable
      patch.diff       the exact change that was tested
  ai/                  Gemma's raw answers and the exact prompts sent
  _work/logs/          full pip and pytest output of the baseline and each candidate run
```

Verify the fingerprints (all 14 matched when this folder was created):

```powershell
python -c "import json,hashlib,pathlib; d=json.load(open('summary.json',encoding='utf-8')); print(all(hashlib.sha256(pathlib.Path(k).read_bytes()).hexdigest()==v for k,v in d['evidence'].items()))"
```

Run it from inside `validation/understatAPI/`; it prints `True`.

Reproduce the run (a fresh run may choose different Gemma answers; to repeat these exact plans, keep `ai/`):

```powershell
python -m depexit analyze https://github.com/collinb9/understatAPI --review --out validation_run
```

The logs and `summary.json` contain absolute paths from the machine the run was made on (a local Windows folder).
They are left as produced.
